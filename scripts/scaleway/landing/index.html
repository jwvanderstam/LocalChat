Why this exists

Scaleway is a European cloud provider — French-owned, operating data centres in Paris, Amsterdam and Warsaw under EU jurisdiction. For organisations whose sovereignty requirements demand a European infrastructure provider, that makes it one of the few alternatives to hosting everything themselves. Self-hosting is the safe answer to those requirements and also the expensive one: hardware, patching, backups, and someone on call. The question this proof of concept asks is whether a sovereign cloud can carry that load instead. It tests three things: how far deployment can be automated, how billing behaves, and how easy the platform is to work with.

The application under test is LocalChat — a self-hosted RAG application that had only ever run on a workstation and in Docker. Running it there says nothing about running it on someone else's infrastructure. So the test is not whether it can be made to run on Scaleway once, by hand, but whether the entire stack can be deployed automatically, from nothing, by scripts, and taken down the same way.

The answer is yes, with conditions. The stack — application container, PostgreSQL with pgvector, and a model host on a private network — has been built from an empty project and destroyed again five times, each cycle scripted end to end, for about two euros in total. What it needed to get there:

  • Scripts written after the first manual deploy, not before. Every one of the four commands encodes something the documentation did not say — a memory unit the API demands, a status that flickers to error before settling, a network that refuses deletion until its attachments have quietly released.
  • A gate, not a checklist. A verification script that signs in, ingests a document and retrieves it with a query sharing no words with the text. A deploy is a deploy only when that exits zero.
  • A brake. The platform has no spend cap. The teardown is a script that deletes rather than stops, because a stopped machine still bills.
  • A way in. A box that never came up could not be diagnosed, only rebuilt. An SSH key registered in the right project is the difference between a cause and a guess.

The strong points

Idle costs nothing: the database scales to zero and the container is pinned to one instance. Nothing in the product was rewritten to fit the platform. The cheap part of the stack — everything but a GPU — is cents per hour, so a mistake costs a rebuild, not a bill. And what the scripts encode is now reusable: the same commands, with prefixed and defaulted settings, would stand the stack up in another account.

The attention points

Nothing stops spend automatically; a budget alert lags the invoice, so the brake is discipline plus a script. Encryption to the database is structural — an unencrypted connection cannot even name its target. The managed environment exposes assumptions a workstation covers: a health check that never checked, a retrieval path that silently stores nothing without its model host. Diagnosis on a managed instance needs preparation — console and key — before the failure, not after. And the one expensive component, a GPU, was scarce on the day it was checked; a plan that assumes it is available on demand is a plan that waits.

What was built

LocalChat lets people upload documents and ask questions about them, with retrieval over a vector database and a locally hosted language model. This proof of concept answers one question: can it run on managed cloud infrastructure without changing what the product is?

It can. The stack is a Serverless Container running the application, a Serverless SQL Database with pgvector for retrieval, and a small Instance serving the embedding model over a private network. No component was rewritten to fit the platform.

How to deploy it

Four commands. All of them are idempotent: running one twice does nothing the second time. They were written after deploying once by hand, so they encode what actually worked rather than what the documentation predicted.

bash   scripts/scaleway/provision.sh          # project, database, scoped credentials
bash   scripts/scaleway/deploy_container.sh   # the application
python scripts/scaleway/verify_deployment.py <endpoint>
bash   scripts/scaleway/deploy_embeddings.sh  # the embedding model host

The third command is a gate rather than a checklist. It signs in, confirms the deployed image is the version you think it is, ingests a document and retrieves it with a query that shares no words with the text — so a passing result can only come from the vector search actually working. It exits non-zero on failure.

Stopping the costs

The platform has no spend cap at any level, so the teardown is a script rather than a habit:

PROJECT_ID=<project> bash scripts/scaleway/panic_teardown.sh                  # shows what would go
PROJECT_ID=<project> CONFIRM=DESTROY bash scripts/scaleway/panic_teardown.sh  # stops it

It deletes rather than stops, because a stopped machine keeps billing for its disks and its reserved address. It refuses to touch anything outside the project it was given.

What the deployment disproved

Three things the plan believed turned out to be wrong, and finding them is most of the value of running a proof of concept at all.

Retrieval does not work without the model host

The plan assumed a first pass without any language model would still validate document upload and search. It does not: every document chunk is embedded through the model host, so with none reachable nothing is stored at all. The fix was not an expensive GPU — embeddings alone run acceptably on a small CPU machine, at roughly two cents an hour.

Encryption to the database is structural, not optional

The managed database selects which database you reach from the encrypted handshake itself. An unencrypted connection cannot name its target, so it fails with a confusing error rather than a security warning. The application had never made this setting explicit; it does now.

A health check that never checked

The application's health endpoint reported the database as healthy for the life of the process, because it echoed a flag recorded at startup rather than asking the database anything. On a server that is always running, this behaves like correct code indefinitely. On a database that scales to zero, it reports green while every request fails.

This was a latent defect, not a platform requirement — the cloud only made it visible. That is the most transferable lesson here: when moving to managed infrastructure, look for the assumptions an always-present environment was quietly covering.

What it cost

About two euros for the entire exercise — database, application container, model host, private networking, stood up and torn down five times over ten days. Most of it went to one stack that was left standing for two days between sessions. The figure matters less than the shape behind it:

  • Idle costs nothing. The database scales to zero; the application was pinned to a single instance on purpose, so concurrency cannot multiply the bill.
  • A GPU is the only expensive decision. Text generation needs one, at roughly €575 per month if left running. Everything else is cents.
  • Nothing stops spend automatically. A budget alert is an estimate that lags the invoice. The teardown script is the actual brake.

The sequencing that made this cheap: prove the plumbing on a two-cent machine, so that when an expensive one is finally switched on it has exactly one question left to answer.

Where it stands

The document path — upload, embed, store, retrieve — works on this infrastructure and has been verified on every cycle. Text generation has been run on the CPU host: the answer is correct and cites the source, but at half a minute to the first word. The open decision is a GPU instance for the same host, at €0.787 per hour while it runs — the plan is to build it beside the CPU machine for a two-hour session, measure, and tear it down. The alternative, a hosted model API, is cheaper to run and a change to what the product is rather than to how it is deployed.

The stack is currently torn down. It rebuilds from the four commands above.
